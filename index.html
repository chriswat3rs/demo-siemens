    Arquitectura de la solución

    Qué se necesita para producción y cómo opera el portal una vez conectado al stack Microsoft del tenant de Siemens Healthineers.
    Estado actual: prototipo con datos simulados en el navegador. Esta página describe la arquitectura objetivo — todos los componentes son Microsoft-native, dentro de la gobernanza del tenant.

    Diagrama de arquitectura objetivo

    los números corresponden al flujo descrito abajo

    Cómo trabaja el portal conectado — flujo de una solicitud

    1
    El usuario entra al portal desde el navegador. No hay datos locales: todo se lee y escribe contra el tenant.
    2
    Entra ID autentica vía MSAL (OAuth 2.0/OIDC). El rol del usuario (solicitante vs. equipo legal) define qué vistas y acciones ve.
    3
    Al enviar el formulario, el portal crea el registro en SharePoint (Graph API o conector): ticket ID único, los 8 criterios, adjuntos y timestamp.
    4
    La creación del registro dispara Power Automate: aplica las reglas de ruteo (país, área, tipo, naturaleza) y calcula el SLA objetivo.
    5
    El flujo notifica por Outlook/Teams al responsable asignado y al solicitante con el ticket ID y el plazo.
    6
    Si la naturaleza es pública, se activa la ruta adicional de Compliance antes de continuar.
    7
    Cada cambio de estado en la cola escribe de vuelta en SharePoint (historial auditable). Power BI se refresca desde la misma lista — sin reporte manual.
    8
    El informe Power BI se embebe de vuelta en el portal (Power BI Embedded o secure embed), como viste en la página de Métricas.

    Checklist de habilitación para IT

    A
    App registration en Entra ID — client ID, redirect URIs, permisos delegados de Graph (Sites.ReadWrite, Mail.Send).
    B
    Sitio SharePoint aprovisionado — estructura para solución cross-country LAM y modelo de permisos por rol.
    C
    Licenciamiento Power Automate — conectores estándar bastan (SharePoint, Outlook); Premium solo si se usa HTTP/Graph directo.
    D
    Power BI — workspace, licencias Pro del equipo o capacidad Embedded para incrustar en el portal.
    E
    Gobernanza — residencia de datos LAM, políticas de retención y alineación con el CoE de Power Platform si existe.
    F
    Punto de contacto técnico asignado durante el build (compromiso del deck de João y Lina).
